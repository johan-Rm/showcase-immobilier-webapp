# Auto Imports And Aliases

- Role: documenter les groupes auto-importes Nuxt et les alias de resolution du projet.
- Related: [./1.application-architecture.md](./1.application-architecture.md), [./5.responsibility-boundaries.md](./5.responsibility-boundaries.md), [../../app/composables/README.md](../../app/composables/README.md), [../../app/utils/README.md](../../app/utils/README.md), [../../app/stores/README.md](../../app/stores/README.md)

## Intent

Ce document clarifie ce qui peut etre consomme sans import explicite et quels alias doivent etre
privilegies selon la couche concernee.

L objectif est de garder les imports lisibles, stables et alignes avec les frontieres du projet.

## Source Of Truth

Les sources stables sont :

- `nuxt.config.ts` pour les alias configures explicitement
- `tsconfig.json` pour les alias exposes a TypeScript
- `.nuxt/imports.d.ts` apres `bunx nuxi prepare` pour les auto-imports effectivement generes
- `.nuxt/tsconfig.json` apres `bunx nuxi prepare` pour les alias effectivement resolus par Nuxt

Les fichiers `.nuxt/*` sont des artefacts generes. Ils servent a verifier l etat reel, mais ne
doivent pas porter de convention manuelle.

## Auto Import Groups

### `app/composables/`

Nuxt auto-importe les exports du premier niveau de `app/composables/`.

Usage attendu :

- composables `useXxx` exposes a l UI
- orchestration reactive reutilisable
- passerelles lisibles entre composants, stores, routeur, i18n et services

Contraintes :

- un composable garde une responsabilite dominante
- la logique metier partagee reste dans `services/` quand elle n a pas besoin de Vue
- les sous-dossiers ne sont pas auto-importes par defaut sans re-export ou configuration dediee

### `app/utils/`

Nuxt auto-importe les exports du premier niveau de `app/utils/`.

Usage attendu :

- helpers legers pour l app Nuxt
- fonctions pures, sans dependance au contexte de route, store ou DOM

Si un helper devient partageable hors app Vue, le placer plutot dans `shared/utils/`.

### `shared/utils/`

Nuxt expose aussi les utilitaires partages presents dans `shared/utils/`.

Usage attendu :

- helpers framework-agnostic
- fonctions reutilisables par `app/`, `services/` et potentiellement `server/`

Ces utilitaires ne doivent pas dependre de Vue, Nuxt, Pinia ou du DOM.

### `shared/types/`

Les types partages de `shared/types/` sont auto-importes dans le contexte Nuxt.

Usage attendu :

- contrats transverses simples
- types applicatifs partages entre UI, stores, services et serveur

Pour les frontieres de donnees plus structurees, privilegier les contrats de `schemas/` et les
types explicitement importes depuis `@schemas`.

### `app/stores/`

Le module Pinia/Nuxt expose les stores sous forme `useXxxStore`.

Usage attendu :

- etat global partage
- cache front et orchestration de donnees applicatives
- mutations via actions explicites

Dans `app/stores/`, ne pas importer explicitement les API Pinia deja auto-importees quand elles
sont disponibles, notamment `defineStore`.

### Framework And Modules

Nuxt auto-importe aussi des APIs de framework et de modules :

- Nuxt app, routing, data fetching, SEO et runtime config
- Vue reactivity et lifecycle
- Vue Router
- VueUse
- Pinia
- i18n
- Nuxt Image
- Nuxt UI
- Nuxt MDC
- Device
- Color Mode
- Sitemap et Site Config

Ces auto-imports sont acceptes quand ils restent explicites par leur nom. Pour des APIs peu
courantes ou ambigues, un import explicite peut rester preferable pour la lisibilite.

## Project Aliases

| Alias                           | Cible                       | Usage recommande                                  |
| ------------------------------- | --------------------------- | ------------------------------------------------- |
| `~`, `~/...`                    | `app/`                      | imports applicatifs depuis l app Nuxt             |
| `@`, `@/...`                    | `app/`                      | equivalent de `~`, a eviter si `~` est deja clair |
| `~~`, `~~/...`                  | racine projet               | acces ponctuel a un fichier hors `app/`           |
| `@@`, `@@/...`                  | racine projet               | equivalent de `~~`, usage rare                    |
| `#shared`, `#shared/...`        | `shared/`                   | contrats et helpers partages                      |
| `#server`, `#server/...`        | `server/`                   | imports serveur Nitro                             |
| `@schemas`, `@schemas/...`      | `schemas/`                  | schemas, interfaces et DTOs                       |
| `@services`, `@services/...`    | `services/`                 | logique metier, loaders, mappers, integrations    |
| `@utils`, `@utils/...`          | `app/utils/`                | utils app Nuxt                                    |
| `@locales`                      | `i18n/locales/`             | ressources locales legacy ou dediees              |
| `@content`, `@content/...`      | `content/`                  | contenu editorial structure                       |
| `@DigitalOrchestrationCore/...` | chemin externe configurable | integration optionnelle via variable d env        |

## Nuxt And Module Aliases

Ces alias sont fournis par Nuxt ou par les modules installes :

| Alias                    | Usage                         |
| ------------------------ | ----------------------------- |
| `#imports`               | imports generes Nuxt          |
| `#app`, `#app/...`       | runtime Nuxt                  |
| `#components`            | composants auto-importes Nuxt |
| `#ui`, `#ui/...`         | runtime Nuxt UI               |
| `#i18n`, `#i18n-kit/...` | runtime et kit i18n           |
| `#sitemap`, `#sitemap/*` | runtime sitemap               |
| `#site-config/...`       | runtime site-config           |
| `#vue-router`            | Vue Router                    |
| `#unhead/composables`    | composables head/meta         |

Ces alias sont utiles pour les modules et certains cas techniques. Dans le code applicatif courant,
preferer les auto-imports Nuxt ou les alias projet plus lisibles.

## Usage Rules

- Preferer les auto-imports pour les APIs Nuxt/Vue courantes, les composables projet et les stores.
- Preferer les imports explicites pour les types venant de `@schemas`, les services et les modules
  externes non auto-importes.
- Eviter les chemins relatifs profonds quand un alias stable existe.
- Ne pas importer depuis `.nuxt/*` dans le code source applicatif.
- Ne pas ajouter d alias sans benefice clair de lisibilite ou de frontiere architecturale.
- Garder les services framework-agnostic : ils ne doivent pas dependre de `#imports`, `~` vers
  `app/`, Vue ou Nuxt.
- Verifier les auto-imports apres ajout ou deplacement de fichiers avec `bunx nuxi prepare`.

## Operational Summary

Pour choisir un import :

1. API Nuxt, Vue, Pinia ou composable projet courant -> auto-import.
2. Fichier dans `app/` -> `~/...`.
3. Service metier -> `@services/...`.
4. Contrat schema ou DTO -> `@schemas/...`.
5. Helper partage hors Vue -> `#shared/...` ou auto-import si deja expose.
6. Fichier racine exceptionnel -> `~~/...`.
