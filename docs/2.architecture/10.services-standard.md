# Services Standard

- Role: définir les conventions de la couche `services/`, ses sous-dossiers et leurs invariants.
- Related: [./1.application-architecture.md](./1.application-architecture.md), [./5.responsibility-boundaries.md](./5.responsibility-boundaries.md), [../../services/README.md](../../services/README.md)

## Intent

Ce document fixe ce qu'est un service dans ce projet, comment la couche est organisée,
et quand créer un service plutôt qu'un composable ou un utilitaire.

La règle centrale est simple : **un service est framework-agnostic**. Il ne doit pas
dépendre de Vue, Nuxt, Pinia ou du DOM. Cette contrainte le rend testable unitairement
et réutilisable hors contexte UI.

## Règle fondamentale

Un fichier dans `services/` ne doit importer ni `vue`, ni `#imports`, ni `~/...` vers `app/`.

Imports autorisés dans un service :

- `node:*` pour les outils système
- bibliothèques tierces pures (ex: `yaml`, `zod`)
- `@schemas/...` pour les contrats de données
- `#shared/...` pour les utilitaires partagés
- d'autres services dans `services/`

## Organisation des sous-dossiers

### `mapper/`

Transforme des données brutes ou hétérogènes en contrats applicatifs stables.

Caractéristiques :

- accepte des entrées partielles, des slugs ou des objets selon la source
- résout les relations via des index en mémoire (`Map`) construits une seule fois
- produit un contrat typé consommable directement par les stores et l'UI
- aucun accès I/O, aucun effet de bord

Pattern typique :

```ts
// Entrée : données brutes provenant d'un loader
// Sortie : contrat `Accommodation` stable pour le store

export const mapAccommodations = (
  items: Accommodation[],
  metadata: AccommodationMetadata = {},
): Accommodation[] => {
  const indexes = buildIndexes(metadata)
  return items.map((item) => mapAccommodationWithIndexes(item, indexes))
}
```

Règles :

- construire les indexes une seule fois pour une liste, pas à chaque élément
- préférer des helpers purs et nommés (`mapCategory`, `mapPlace`) à une fonction monolithique
- ne jamais `throw` sur une donnée manquante : utiliser un fallback contractualisé

### `content/`

Parseurs synchrones du contenu éditorial.

Rôle : extraire des structures applicatives depuis le corps Markdown/MDC des pages.

Ce n'est pas le runtime `@nuxtjs/mdc`. C'est un sous-ensemble synchrone et déterministe
adapté aux besoins des stores et des getters, où le parsing asynchrone ne peut pas être
utilisé directement.

### `converter/`

Transformations lourdes de bas niveau, utilisées principalement au build.

Exemple : `converter/schema/generateArtifacts.ts` convertit des fichiers YAML en
interfaces TypeScript.

Un converter traite un format source vers un format cible. Il n'a pas de connaissance
du domaine métier — il connaît uniquement la structure syntaxique de sa source.

### `hooks/`

Orchestrateurs build-time Nuxt.

Un hook ne contient pas de logique métier. Il :

- résout les chemins et ressources nécessaires
- délègue le travail à des services `infra/`, `converter/` ou `mapper/`
- centralise le reporting et la gestion d'erreurs

Point d'entrée : le hook `build:before` dans `nuxt.config.ts`.

### `infra/`

Résolution d'infrastructure : chemins, variables d'environnement, accès système.

Un service `infra/` est la seule couche autorisée à lire `process.env` ou à résoudre
des chemins absolus. Il isole les dépendances système pour que les converters et mappers
restent purs.

### `seo/`

Builders purs de métadonnées et de noeuds JSON-LD.

Ces fonctions acceptent des contrats applicatifs normalisés et produisent des objets
directement compatibles avec `useSeoMeta` et les scripts JSON-LD.

Ils ne doivent pas être appelés depuis un service qui n'est pas déjà dans un contexte
page (la construction des URLs absolues suppose un `siteUrl` résolu côté appelant).

### `api/`

Clients d'appel HTTP avec inversion de contrôle.

Le fetcher est injecté par le composable appelant (`$fetch`, `useFetch`, mock de test),
ce qui rend le service testable sans dépendance au runtime Nuxt.

```ts
export const postEcho = async (
  input: EchoRequest,
  fetcher: JsonFetcher,
): Promise<EchoResponse> => {
  const payload = echoRequestSchema.parse(input)
  const data = await fetcher<unknown>('/api/echo', { method: 'POST', body: payload })
  return echoResponseSchema.parse(data)
}
```

Règle : valider l'entrée et la sortie avec les schémas Zod correspondants.

### `utils/`

Helpers purs propres à la couche services.

Si un helper devient utile hors `services/`, le déplacer dans `shared/utils/`.

## Quand créer un service

| Situation | Couche recommandée |
|---|---|
| Transformation DTO → contrat applicatif | `services/mapper/` |
| Parsing synchrone de contenu éditorial | `services/content/` |
| Génération d'artefacts au build | `services/converter/` + `services/hooks/` |
| Résolution de chemins ou de variables d'env | `services/infra/` |
| Construction de noeuds SEO / JSON-LD | `services/seo/` |
| Appel HTTP avec validation Zod | `services/api/` |
| Logique réactive liée à Vue | `app/composables/` |
| Helper léger sans état | `app/utils/` ou `shared/utils/` |

## Invariants

- un service ne dépend pas de Vue, Nuxt, Pinia ou du DOM
- un service reçoit ses dépendances par paramètre, pas via des auto-imports Nuxt
- un service peut être testé unitairement sans `mountComponent` ni `setup`
- les effets de bord (I/O, réseau, écriture fichier) sont limités à `hooks/` et `infra/`
- `mapper/` et `seo/` sont purs : mêmes entrées → mêmes sorties, sans effet observable

## Ce qu'un service ne fait pas

- accéder au store Pinia (`useXxxStore`)
- appeler `useRoute`, `useRuntimeConfig` ou tout composable Nuxt
- manipuler le DOM ou lire `window`
- contenir de la logique d'orchestration UI (transitions, ancres, état d'affichage)
