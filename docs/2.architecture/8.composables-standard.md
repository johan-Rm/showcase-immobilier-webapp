# Composables Standard

## Rôle

Les composables ont pour responsabilité d’orchestrer la logique réactive liée à Vue/Nuxt :

- gestion de l’état réactif
- orchestration des données
- synchronisation UI / URL / cycle de vie
- encapsulation de comportements réutilisables
- composition de fonctionnalités métier

Un composable ne doit pas devenir un “God Object” ni une couche métier globale implicite.

---

# Structure recommandée

```ts
export const useFeature = () => {
  /**
   * State
   */
  const isLoading = ref(false)

  /**
   * Derived state
   */
  const hasData = computed(() => {
    return true
  })

  /**
   * Actions
   */
  const load = async () => {}

  /**
   * Lifecycle
   */
  onMounted(() => {
    load()
  })

  return {
    isLoading,
    hasData,
    load,
  }
}
```

# Conventions techniques

## Responsabilité unique

Un composable doit avoir une responsabilité claire et identifiable.

✅ Correct

- `useSearch()`
- `useUserProfile()`
- `useInfiniteScroll()`

❌ Incorrect

- `useApp()`
- `useGlobalStuff()`
- `useHelpers()`

---

## API explicite

Le nom des variables et méthodes exposées doit refléter le métier.

✅ Correct

```ts
return {
  users,
  isLoading,
  refreshUsers,
}
```

❌ Incorrect

```ts
return {
  data,
  loading,
  execute,
}
```

---

## Side effects explicites

Les appels API ou comportements critiques ne doivent pas être cachés implicitement.

❌ Incorrect

```ts
export const useUser = () => {
  fetchUser()
}
```

✅ Correct

```ts
const { loadUser } = useUser()

await loadUser()
```

---

## Limiter les watchers

Les `watch()` doivent rester rares et justifiés.

Cas légitimes :

- synchronisation URL
- déclenchement API
- interaction externe
- side effects contrôlés

Préférer :

- `computed`
- architecture déclarative
- événements explicites

---

## Éviter les composables “magiques”

Un composable ne doit pas :

- modifier silencieusement des stores
- déclencher des analytics cachés
- lancer plusieurs appels réseau implicites
- produire des effets de bord invisibles

Les effets doivent être lisibles et prévisibles.

---

## Séparer orchestration et logique métier

Les composables orchestrent la réactivité Vue.

La logique métier pure doit être externalisée dans :

- `services/`
- `utils/`
- fonctions pures

✅ Correct

```ts
const normalizedUsers = normalizeUsers(users)
```

❌ Incorrect

50 lignes de transformation métier directement dans le composable.

---

## Limiter la taille des composables

Un composable trop volumineux cache généralement plusieurs responsabilités.

Signaux d’alerte :

- centaines de lignes
- nombreux watchers
- logique métier dense
- multiples responsabilités

Préférer l’extraction en plusieurs composables spécialisés.

---

## Distinguer état local et état partagé

Un composable doit clairement exprimer s’il :

- crée un état local
- partage un état global

✅ État local

```ts
export const useCounter = () => {
  const count = ref(0)
}
```

✅ État partagé

```ts
const count = useState('count', () => 0)
```

---

## Préférer les composables orientés feature

Préférer des composables métier cohérents :

✅ Correct

- `useProductSearch()`
- `useBookingCalendar()`
- `usePropertyFilters()`

Plutôt qu’une accumulation de micro-composables techniques difficilement lisibles.

---

## Documentation des effets

Les comportements importants doivent être documentés.

```ts
/**
 * Synchronise les filtres avec l'URL
 * et déclenche automatiquement un refresh API.
 */
```

---

# Anti-patterns

## ❌ Composable “God Object”

```ts
useApp()
```

gérant :

- auth
- websocket
- analytics
- notifications
- thème
- cache
- API

---

## ❌ Retour générique

```ts
return {
  data,
  state,
  execute,
}
```

---

## ❌ Appels API implicites

```ts
useSomething()
```

déclenchant automatiquement des fetchs invisibles.

---

## ❌ Multiplication des watchers

```ts
watch(a)
watch(b)
watch(c)
```

---

## ❌ Logique métier massive dans le composable

Transformations complexes, mapping lourd ou règles métier profondes doivent être externalisés.

---

# Philosophie

Un composable doit pouvoir être compris rapidement uniquement en lisant :

- son nom
- ses paramètres
- son `return`

L’objectif est de produire des composables :

- lisibles
- prévisibles
- testables
- réutilisables
- maintenables
