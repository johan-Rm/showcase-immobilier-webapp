# Composables Standard

- Role: définir le rôle des composables dans l'architecture de données du projet et leur standard d'écriture.
- Related: [./2.data-flow.md](./2.data-flow.md), [./5.responsibility-boundaries.md](./5.responsibility-boundaries.md), [./10.services-standard.md](./10.services-standard.md), [./11.stores-standard.md](./11.stores-standard.md), [../../app/composables/README.md](../../app/composables/README.md)

## Rôle

Les composables ont pour responsabilité d'orchestrer la logique réactive liée à Vue/Nuxt :

- gestion de l'état réactif
- orchestration des données
- synchronisation UI / URL / cycle de vie
- encapsulation de comportements réutilisables
- composition de fonctionnalités métier

Un composable ne doit pas devenir un “God Object” ni une couche métier globale implicite.

Les conventions techniques des composables sont portées par le README co-localisé :
[../../app/composables/README.md](../../app/composables/README.md).

## Architecture triptyque : composables, stores, services

La gestion des données repose sur trois couches aux rôles clairs et non superposables.

### Composables — passerelle entre l'UI et la logique applicative

Les composables (`useXxx()`) servent de passerelle entre l'interface utilisateur et la
logique applicative. Ils exposent une API réactive adaptée aux composants tout en
orchestrant les interactions avec les stores, les services et les endpoints internes.

### Stores — état global brut, lecture enrichie

Les stores Pinia (`useXxxStore()`) centralisent l'état global partagé. Le state stocke
les données brutes (DTOs sérialisables) ; les getters délèguent l'enrichissement aux
mappers de `services/mapper/` à la demande — pattern « état brut, getter enrichi ».
Les mutations passent par des setters explicites (`setX`, `reset`). L'UI réagit
automatiquement aux mutations.

Le détail est défini dans [./11.stores-standard.md](./11.stores-standard.md).

### Services — logique métier pure

Les services contiennent la logique métier pure : transformation de données (mappers),
appels vers l'API Symfony, gestion des erreurs, parsing des réponses. Ils sont
**indépendants de Vue, Nuxt et Pinia** (règle CI `verify-no-framework-imports`), ce qui
garantit :

- une testabilité maximale
- une réutilisation possible hors du contexte Nuxt
- qu'aucune fuite de logique métier ne remonte vers les composants

Le détail est défini dans [./10.services-standard.md](./10.services-standard.md).

### La couche BFF (`server/`)

Le frontend ne parle pas directement à l'API Symfony : les routes Nitro internes
(`/api/content/*`, `/api/dashboard/*`, `/api/contact`…) servent de BFF. Elles gardent les
secrets côté serveur, valident les entrées et normalisent les réponses. En SSR, un
`$fetch` vers un endpoint interne appelle le handler directement, sans requête HTTP.

## Flux général des données

1. L'utilisateur interagit avec l'UI (pages, composants).
2. Les composants invoquent les composables (`useXxx`).
3. Les composables s'appuient sur les stores, les services, ou appellent directement un
   endpoint BFF interne.
4. Le BFF et les services communiquent avec l'API Symfony.
5. Le store se met à jour → les getters enrichis recalculent → l'UI se re-rend.

## Frontières réseau

- **Un composant n'appelle jamais l'API** — ni interne, ni externe
  (règle YAML `app-no-fetch-in-components`). Il reçoit ses données via props ou composable.
- **Un composable ou une page peut appeler un endpoint Nitro interne** directement via
  `$fetch` : c'est la couche serveur de la même application.
- **Les appels vers l'API Symfony externe** passent par `services/api/` (côté client) ou
  par le BFF (côté serveur) — jamais en direct depuis un composable.
- **Un composable peut appeler un service directement** si l'état produit n'a pas vocation
  à être global ; sinon il passe par le store.

## Structure recommandée

```ts
export const useFeature = () => {
  /**
   * State
   */
  const isLoading = ref(false)

  /**
   * Derived state
   */
  const hasData = computed(() => {
    return true
  })

  /**
   * Actions
   */
  const load = async () => {}

  /**
   * Lifecycle
   */
  onMounted(() => {
    load()
  })

  return {
    isLoading,
    hasData,
    load,
  }
}
```

## Philosophie

Un composable doit pouvoir être compris rapidement uniquement en lisant :

- son nom
- ses paramètres
- son `return`

L'objectif est de produire des composables :

- lisibles
- prévisibles
- testables
- réutilisables
- maintenables
