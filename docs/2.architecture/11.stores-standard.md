# Stores Standard

- Role: définir les conventions des stores Pinia du projet.
- Related: [./1.application-architecture.md](./1.application-architecture.md), [./5.responsibility-boundaries.md](./5.responsibility-boundaries.md), [./10.services-standard.md](./10.services-standard.md), [../../app/stores/README.md](../../app/stores/README.md)

## Intent

Ce document fixe comment les stores Pinia sont organisés dans ce projet, quels patterns
ils appliquent et ce qu'ils ne doivent pas faire.

Un store centralise l'état global partagé entre plusieurs composants ou composables. Il ne
porte pas la logique métier — il la délègue aux services. Il ne connaît pas l'UI — il
expose un contrat typé que les composables consomment.

## Deux styles de store

Le projet utilise les deux syntaxes Pinia selon la nature du store.

### Options API — stores de données

Pour les stores qui gèrent des listes ou des entités stables chargées depuis le contenu.

```ts
type WebPageState = {
  list: WebPageDto[]
}

export const useWebPageStore = defineStore('webPage', {
  state: (): WebPageState => ({
    list: [],
  }),

  getters: {
    getWebPages(state): WebPage[] {
      const metadataStore = useMetadataStore()
      return mapWebPages(state.list, metadataStore.getCategoryCodes, ...)
    },
  },

  actions: {
    setList(pages: WebPageDto[]): void {
      this.list = mergeListByKey(this.list, pages, { getKey: (p) => p.slug ?? '' })
    },

    reset(): void {
      this.list = []
    },
  },
})
```

Utiliser ce style quand :

- le store maintient des listes ou entités persistantes
- le state est rechargé à chaque changement de locale ou de bootstrap
- les getters enrichissent les données brutes via des mappers

### Composition API — stores transients

Pour les stores qui gèrent une opération asynchrone avec état de chargement.

```ts
export const useEchoStore = defineStore('echo', () => {
  const echoed = ref<string | null>(null)
  const loading = ref(false)
  const error = ref<ApiError | null>(null)

  const sendEcho = async (payload: EchoRequest): Promise<EchoResponse | null> => {
    loading.value = true
    error.value = null
    try {
      const response = await postEcho(payload, $fetch as JsonFetcher)
      echoed.value = response.echoed
      return response
    } catch (err) {
      error.value = normalizeApiError(err)
      return null
    } finally {
      loading.value = false
    }
  }

  return { echoed, loading, error, sendEcho }
})
```

Utiliser ce style quand :

- le store orchestre une requête asynchrone unique
- un état `loading` et `error` est nécessaire
- le state est transient et n'a pas besoin d'être rechargé à la locale

## Pattern central : état brut, getter enrichi

Le state stocke les données brutes (DTOs, contenu parsé).
Les getters délèguent l'enrichissement aux mappers de `services/mapper/`.

```
state.list (WebPageDto[])
  → getter getWebPages() appelle mapWebPages()
    → retourne WebPage[] prêts pour l'UI
```

Avantages :

- le state reste sérialisable pour le SSR
- le mapping n'est calculé qu'à la demande
- le state peut être rechargé sans casser les références de getters

## Conventions d'actions

### Setters explicites

Les mutations d'état passent par des actions nommées `setX`.

```ts
setList(pages: WebPageDto[]): void
setApp(item: App | null): void
setAccommodationCategories(items: AccommodationCategory[]): void
```

Règle : toujours défensif sur le type d'entrée — valider avec `Array.isArray` ou un guard
avant d'assigner, pour absorber les sources hétérogènes sans planter.

### `reset()` systématique

Chaque store expose une action `reset()` qui ramène l'état à sa valeur initiale.

Le bootstrap global (`useNuxtServerInit`) appelle `reset()` sur les stores avant
de recharger les données lorsque la locale change.

### Merge stable pour les listes

Pour les listes rechargées partiellement, utiliser `mergeListByKey` plutôt qu'un
remplacement brutal. Cela préserve la réactivité sans provoquer de re-rendu global.

```ts
this.list = mergeListByKey(this.list, next, { getKey: (item) => item.slug ?? '' })
```

### Async avec flags `loading` / `error`

Dans les stores composition API, encadrer chaque opération async avec les flags standard.

```ts
loading.value = true
error.value = null
try {
  // ...
} catch (err) {
  error.value = normalizeApiError(err)
} finally {
  loading.value = false
}
```

## Dépendances entre stores

Un getter peut appeler un autre store pour accéder à ses données de référence.

```ts
getAccommodations(state): Accommodation[] {
  const metadataStore = useMetadataStore()
  return mapAccommodations(state.list, {
    categories: metadataStore.getAccommodationCategories,
    images: metadataStore.getImageObjects,
    // ...
  })
}
```

Règle : les dépendances entre stores se font uniquement dans les getters, jamais dans
les actions. Une action ne doit pas dépendre du résultat d'un getter d'un autre store.

## Règles SSR

- le state ne doit contenir que des valeurs sérialisables (pas de `ref`, pas d'objets DOM)
- les actions qui déclenchent des effets de bord doivent être gardées côté client si
  elles dépendent de `window` ou de contextes client-only
- `defineStore` est auto-importé par Nuxt : ne pas l'importer manuellement

## Ce qu'un store ne fait pas

- porter la logique de transformation métier (rôle des services `mapper/`)
- appeler directement une API réseau (déléguer à `services/api/`)
- connaître les composants qui le consomment
- contenir de la logique de navigation ou d'affichage
- exposer des valeurs non typées

## Naming

| Élément                 | Convention                                                   |
| ----------------------- | ------------------------------------------------------------ |
| Fichier                 | `camelCase.ts` — ex: `webPage.ts`                            |
| Export                  | `useXxxStore` — ex: `useWebPageStore`                        |
| Clé Pinia               | `'camelCase'` identique au nom de domaine                    |
| État                    | type local `XxxState` déclaré dans le fichier                |
| Getter de liste         | `getXxx` — retourne un tableau enrichi                       |
| Getter de lookup        | `getXxxBySlug`, `getXxxByIdentifier` — retourne une fonction |
| Action setter           | `setX` — mutation d'un champ ou d'une liste                  |
| Action réinitialisation | `reset` — toujours présente                                  |
