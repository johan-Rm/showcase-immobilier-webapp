# Content Model

- Role: documenter l'organisation de `content/`, les types de ressources et le pipeline de transformation vers les contrats applicatifs.
- Related: [./1.application-architecture.md](./1.application-architecture.md), [./2.data-flow.md](./2.data-flow.md), [../../content/README.md](../../content/README.md), [../../services/README.md](../../services/README.md)

## Intent

Ce document explique comment le contenu éditorial est organisé dans `content/`, comment
chaque type de fichier correspond à un contrat schema.org, et comment il traverse la
pipeline pour atteindre l'UI.

`content/` est la source de vérité du contenu métier. Aucune logique de parsing ou
d'enrichissement ne doit y résider — c'est le rôle des services et des stores.

## Structure par locale

```text
content/{lang}/
├── app.yaml                    ← config UI globale (labels, menus, sections)
├── messages.ts                 ← traductions i18n de la locale
├── real-estate-listing.yaml    ← référentiel des types de listings
├── accommodation-category.yaml ← catégories de biens
├── accommodation-place.yaml    ← lieux géographiques référencés
├── category-code.yaml          ← codes transverses (tags, amenities)
├── person.yaml                 ← agents et contacts
├── media-object.yaml           ← référentiel UUID → objets médias
├── accommodations/             ← fiches de biens immobiliers
│   └── *.md
└── web-pages/                  ← pages éditoriales
    └── *.md
```

Les clés et identifiants doivent rester stables entre locales. Seuls les libellés
et contenus textuels varient selon la langue.

## Types de ressources

### Référentiels YAML

Fichiers plats portant des listes de ressources nommées.

| Fichier | Contrat applicatif | Rôle |
|---|---|---|
| `app.yaml` | `App` | Config UI globale, navigation, labels |
| `real-estate-listing.yaml` | `RealEstateListing[]` | Types de listings (vente, location…) |
| `accommodation-category.yaml` | `AccommodationCategory[]` | Catégories de biens |
| `accommodation-place.yaml` | `AccommodationPlace[]` | Lieux géographiques |
| `category-code.yaml` | `CategoryCode[]` | Codes transverses (tags, amenities) |
| `person.yaml` | `Person[]` | Agents et contacts |
| `media-object.yaml` | `MediaObject[]` | Référentiel UUID → objet média |

Ces fichiers sont chargés comme référentiels. Leurs données alimentent les indexes
utilisés par les mappers pour enrichir les biens et les pages.

### Fiches `accommodations/*.md`

Chaque fichier représente un bien immobilier.

Format : Markdown avec frontmatter YAML dense.

Le frontmatter porte l'ensemble des données métier :
- identifiant, slug, catégorie, lieu, listing
- offre (prix, devise)
- surfaces, pièces, médias
- tags, agent, état actif

Le body Markdown est la description éditoriale libre du bien (sections de visite guidée).
Il ne contient pas de blocs MDC.

Exemple de frontmatter minimal :

```yaml
---
identifier: BAVR001
slug: riad-boutique-renove-medina-bavr001
category: riad
realEstateListing: bien-a-vendre
place: medina
offer:
  price: 1750000
  priceCurrency: EUR
isActive: true
---
```

Convention d'identifiant : `INITIALES(realEstateListing) + INITIALES(category) + compteur 3 chiffres`.
Voir [content/README.md](../../content/README.md) pour la règle complète.

### Pages éditoriales `web-pages/*.md`

Chaque fichier représente une page éditoriale liée à une route.

Format : Markdown avec frontmatter YAML + blocs MDC dans le body.

Le frontmatter porte les métadonnées SEO et éditoriales :

```yaml
---
slug: home
inLanguage: fr
headline: MLK – My Little Kasbah
metaTitle: MLK – My Little Kasbah | Immobilier à Essaouira
metaDescription: ...
image:
  - uuid-image
articleSection: agence-immobiliere
datePublished: '2022-10-11T00:00:00+02:00'
---
```

Le body contient des blocs MDC (`::nom-du-screen`), chacun avec son propre frontmatter YAML :

```md
::screen-landing
---
identifier: screen-real-estate-full-image
headline: MLK - My Little Kasbah
image: uuid-image
links:
  - for-sale
  - seasonal-rental
hasPart:
  - additionalType: mobile-portrait-background
    image: uuid-mobile
---
::
```

Chaque bloc MDC devient un `CreativeWork` via `services/content/mdc.ts`.
L'ensemble des blocs forme `WebPage.hasPart`.

## Correspondance schema.org

Les contrats applicatifs sont alignés sur schema.org :

| Contrat | Type schema.org | Rôle dans l'app |
|---|---|---|
| `WebPage` | `schema:WebPage` | Page éditoriale avec ses écrans |
| `CreativeWork` | `schema:CreativeWork` | Bloc MDC (screen, section, composant) |
| `Accommodation` | `schema:Accommodation` | Bien immobilier |
| `RealEstateListing` | `schema:RealEstateListing` | Catégorie de mise en marché |
| `MediaObject` | `schema:MediaObject` / `ImageObject` | Objet média résolu depuis son UUID |
| `Person` | `schema:Person` | Agent ou contact |
| `CategoryCode` | `schema:CategoryCode` | Code de catégorie (tag, amenity) |

## Pipeline de transformation

```
content/{lang}/*.yaml et *.md   (fichiers statiques)
  ↓  import.meta.glob           (chargeurs TypeScript par locale)
  ↓  services/content/mdc.ts    (extraction des blocs MDC du body)
  stores — state brut            (DTOs, listes non enrichies)
  ↓  getters → services/mapper/ (mappers : résolution des slugs/UUIDs en objets)
  stores — getters enrichis      (WebPage[], Accommodation[] prêts pour l'UI)
  ↓
  app/composables/               (API réactive exposée aux pages)
  ↓
  app/pages/ et app/components/  (rendu)
```

Les références entre ressources (slugs, UUIDs) sont résolues au niveau des getters,
jamais dans le contenu lui-même ni dans les composants.

## Séquence de chargement

Le bootstrap (`useNuxtServerInit`) charge le contenu en trois phases :

1. **`loadMetadata()`** — bloquant, SSR + client  
   Charge les référentiels : app, listings, catégories, lieux, codes, personnes, médias.  
   Résultat stocké dans `useMetadataStore`.

2. **`loadMainData()`** — bloquant, SSR + client  
   Charge les pages éditoriales (`web-pages`).  
   Résultat stocké dans `useWebPageStore`.

3. **`loadBackgroundData()`** — non bloquant, client uniquement (après hydratation)  
   Charge les fiches de biens (`accommodations`).  
   Résultat stocké dans `useAccommodationStore`.

Cette séquence garantit que les pages éditoriales et les métadonnées SEO sont
disponibles pour le rendu serveur, tandis que les biens — plus volumineux — sont
chargés sans bloquer le premier rendu utile.

## Règles

- les identifiants (slugs, UUIDs, `identifier`) sont stables entre locales
- les UUIDs des médias référencés dans le contenu sont résolus depuis `media-object.yaml`
- une fiche `accommodation` ne duplique pas les données des référentiels : elle référence
  les slugs (`category`, `place`, `realEstateListing`) qui seront résolus par le mapper
- une page `web-pages` ne connaît pas les composants Vue qu'elle active : elle déclare
  des blocs `identifier` que la page Nuxt adresse via `hasPart`
- aucune logique de routing ou de navigation ne doit figurer dans `content/`
