# Script Setup Standard

- Role: formaliser un standard de structure pour les composants Vue et Nuxt en `script setup`.
- Related: [./2.application-architecture.md](./2.application-architecture.md), [./6.responsibility-boundaries.md](./6.responsibility-boundaries.md), [../../app/pages/README.md](../../app/pages/README.md)

## Intent

Ce document harmonise la structure des fichiers Vue en `<script setup lang="ts">`.
Il vise a reduire les variations inutiles, a clarifier les responsabilites et a limiter
la logique metier dans la couche d affichage.

## Scope

Le standard s applique en priorite aux fichiers Vue du frontend Nuxt :

- `app/pages/`
- `app/components/`
- `app/composables/` quand un composable expose une API destinee a l UI

Il doit etre adapte au role reel de chaque couche :

- une page orchestre la route, la meta et le chargement de donnees
- un composant affiche et gere des interactions locales
- un composable structure une logique reactive reutilisable

## Core Principles

- un fichier doit avoir une responsabilite dominante
- le template consomme surtout des valeurs deja preparees
- la logique metier ne doit pas fuir dans l affichage
- les effets de bord doivent etre regroupes et explicites
- les acces aux donnees doivent rester faciles a tracer
- toute exception a la structure doit rester locale et justifiable

## Recommended Block Order

L ordre ci-dessous est la convention par defaut. Les blocs inutiles peuvent etre omis.

```vue
<script setup lang="ts">
// 1. Imports
// 2. Types et constantes statiques
// 3. Props et emits
// 4. Composables, stores, routeur
// 5. Etat local
// 6. Data inputs
// 7. Validation et helpers purs
// 8. Computed UI-ready
// 9. Actions et handlers
// 10. Watch et watchEffect
// 11. Metadonnees ecran ou page
// 12. Lifecycle
</script>
```

## Block Guidance

### 1. Imports

- commencer par les imports `type`
- regrouper ensuite les imports runtime
- eviter les imports inutilises et les chemins profonds evitables

### 2. Types et constantes statiques

- declarer ici les types locaux, interfaces simples et constantes stables
- ne pas y cacher de logique metier partagee

### 3. Props et emits

- declarer les contrats au plus haut du fichier
- typer explicitement les frontieres utiles
- garder les defaults simples et previsibles

### 4. Composables, stores, routeur

- regrouper ici `useRoute`, `useRouter`, stores, i18n et composables de contexte
- ne pas melanger cette zone avec des calculs de presentation

### 5. Etat local

- reserver `ref` et `reactive` a l etat vraiment local
- ne pas dupliquer une valeur qui peut rester un `computed`

### 6. Data inputs

Ce bloc regroupe les entrees brutes consommees par le fichier :

- donnees de store
- params de route
- metadata ou config
- contenu deja resolu si necessaire

Ces valeurs ne sont pas encore obligatoirement pretes pour le template.

### 7. Validation et helpers purs

- centraliser ici les verifications utiles aux champs obligatoires
- garder des helpers purs, sans acces DOM ni effet de bord
- sortir la validation partagee dans un utilitaire ou un service

Politique de prudence :

- ne pas `throw` par reflexe dans un composant public
- choisir explicitement entre erreur bloquante, fallback controle ou non-rendu assume
- tenir compte de l impact SSR, UX et SEO

### 8. Computed UI-ready

Le template doit consommer en priorite :

- labels finalises
- booleens `hasX`, `isX`, `canX`
- URLs, listes et variantes d affichage
- objets de presentation deja prepares

Un `computed` doit idealement porter une intention unique.

### 9. Actions et handlers

- regrouper les handlers utilisateur au meme endroit
- preferer des noms d intention : `handleSubmit`, `openGallery`, `closePanel`
- extraire la logique si un handler devient trop large

### 10. Watch et watchEffect

- utiliser `watch` quand la source doit etre explicite
- utiliser `watchEffect` seulement si les dependances implicites sont acceptables
- regrouper les watchers pour eviter des effets disperses

### 11. Metadonnees ecran ou page

Ce bloc concerne surtout :

- `definePageMeta`
- meta reactive de layout ou de screen
- synchronisation avec un composable de meta

Les objets de meta doivent rester simples et lisibles.

### 12. Lifecycle

- garder le lifecycle en fin de fichier
- le reserver a l orchestration
- ne pas y cacher une logique qui devrait vivre dans un helper ou un `watch`

## Template Discipline

Le template doit rester une couche de rendu.

A eviter :

- acces direct au store si une valeur preparee suffit
- logique metier
- conditions complexes imbriquees
- transformations non triviales de donnees

Acceptable :

- conditions simples de rendu
- iteration sur des donnees deja preparees
- branchements UI elementaires

## Naming Guidance

| Type               | Convention                              |
| ------------------ | --------------------------------------- |
| booleen            | `hasX`, `isX`, `canX`                   |
| identifiant        | `xId`, `xIdentifier`                    |
| config brute       | `xConfig`, `xContent`                   |
| derive d affichage | `displayX`, `uiX`                       |
| handler            | `handleX`, `openX`, `closeX`, `toggleX` |

Ces conventions servent la lisibilite. Elles ne remplacent pas le jugement technique.

## Nuxt Guardrails

- rester SSR-safe par defaut
- ne pas introduire de dependance au DOM sans garde explicite
- ne pas deplacer la logique metier dans `pages/` ou `components/`
- utiliser les primitives Nuxt adaptees quand la route pilote le chargement
- garder une frontiere nette entre orchestration de page et affichage

## Allowed Exceptions

Des ecarts sont acceptables si :

- ils simplifient clairement le fichier
- ils evitent une abstraction artificielle
- ils respectent mieux la responsabilite reelle du fichier
- ils ne degradent ni lisibilite, ni stabilite SSR, ni maintenabilite

## Minimal Example

```vue
<script setup lang="ts">
import type { PropertyCardViewModeListl } from '@shared/models/property'

const props = defineProps<{
  item: PropertyCardViewModeListl
}>()

const isFeatured = computed(() => props.item.badges.includes('featured'))
const displayTitle = computed(() => props.item.title)
const displayPrice = computed(() => props.item.priceLabel)

function handleClick() {
  navigateTo(props.item.href)
}
</script>
```

## Operational Summary

Un bon fichier `script setup` permet de comprendre rapidement :

1. d ou viennent les donnees
2. ce qui est valide ou transforme
3. ce que le template consomme
4. quels effets de bord existent
5. quelle est la responsabilite exacte du fichier
