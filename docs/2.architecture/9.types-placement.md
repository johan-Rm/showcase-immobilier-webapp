# Types Placement

- Role: definir les regles de placement des types TypeScript et documenter le script de verification associe.
- Related: [./1.application-architecture.md](./1.application-architecture.md), [./5.responsibility-boundaries.md](./5.responsibility-boundaries.md), [../../shared/types/](../../shared/types/)

## Intent

Ce document fixe les regles de placement des types TypeScript dans le projet.
Il vise a eliminer les doublons, a identifier la source de verite unique pour chaque type partage
et a rendre les violations detectables automatiquement avant un merge.

## Scope

Les regles s appliquent a tous les fichiers `.ts` et `.vue` dans les quatre couches du projet :

- `app/` — composants, pages, composables, stores
- `server/` — routes et handlers Nitro
- `services/` — mappers, SEO, converters
- `shared/` — code cross-couche, dont `shared/types/`

Sont exclus : `node_modules/`, `.nuxt/`, `dist/`.

## Rules

### Regle 1 — Local par defaut

Un type utilise dans un seul fichier reste dans ce fichier.
Il peut s agir d un `.vue`, d un composable, d un store ou d un service.
Aucune extraction n est requise tant que le type n est pas reutilise ailleurs.

### Regle 2 — Migration obligatoire si partage

Des qu un type est importe par un fichier autre que celui ou il est defini,
il doit etre deplace dans `shared/types/`.
Cette regle s applique quelle que soit la couche d origine.

### Regle 3 — Pas de doublon exporte

Le meme nom de type exporte ne peut pas etre defini dans plusieurs fichiers hors `shared/types/`.
Un type dans `shared/types/` est la source de verite unique.

Les types locaux non exportes — par exemple `Props` ou `Emits` dans des composants Vue —
restent autorises tant qu ils ne sont pas importes par un autre fichier.

## Verification Script

### Localisation

```
scripts/ci/app/verify-types-placement.ts
```

### Commande

```bash
bun run check:types
```

### Dependencies

Le script utilise `@typescript-eslint/parser` (deja installe). Aucune nouvelle dependance.

### Architecture

Le script fonctionne en trois phases.

**Phase 1 — Collecte**

Pour chaque fichier dans le perimetre :

- le contenu du bloc `<script>` est extrait pour les fichiers `.vue`
- l AST est parse avec `@typescript-eslint/parser`
- les definitions de types sont extraites (`TSTypeAliasDeclaration`, `TSInterfaceDeclaration`)
- les imports de types sont extraits et resolus vers leur fichier source reel

Les alias du projet sont geres :

| Alias       | Cible              |
| ----------- | ------------------ |
| `~/`        | `app/`             |
| `@/`        | `app/`             |
| `#shared/`  | `shared/`          |
| `@schemas/` | `schemas/`         |
| `@services/`| `services/`        |

**Phase 2 — Analyse**

Deux violations sont detectees :

| Code            | Condition                                                        | Message                                                     |
| --------------- | ---------------------------------------------------------------- | ----------------------------------------------------------- |
| `DUPLICATE`     | Meme nom exporte dans >= 2 fichiers hors `shared/types/`         | Type defini dans A et B → deplacer dans `shared/types/`     |
| `SHOULD_MIGRATE`| Type defini hors `shared/types/` et importe par >= 1 autre fichier | Type defini dans A, importe par B → deplacer dans `shared/types/` |

**Phase 3 — Rapport**

- Aucune violation → `✓ Types placement OK` + `exit 0`
- Violations → liste formatee avec fichier, type et regle enfreinte + `exit 1`

### Exemple de sortie

```
✗ 2 violation(s) detectee(s)

  SHOULD_MIGRATE  app/components/AppLink.vue
                  Type "AppLinkTarget" importe par app/components/screen/Footer.vue
                  → Deplacer dans shared/types/

  DUPLICATE       Type "AccommodationStatus"
                  Defini dans : app/composables/useAccommodation.ts et services/mapper/accommodation.ts
                  → Conserver une seule definition dans shared/types/
```

## What the Script Does Not Check

- Les types definis dans des fichiers `.d.ts` globaux (hors perimetre, geres par TypeScript)
- Les types generes dans `.nuxt/` (exclus du scan)
- La coherence semantique des types (role de `tsc`)

## Decision Tree

```
Type defini dans un fichier
│
├─ Exporte et le meme nom existe dans un autre fichier hors shared/types/ ?
│   └─ OUI → violation DUPLICATE → deplacer dans shared/types/
│
├─ Importe par un fichier autre que le fichier de definition ?
│   └─ OUI → violation SHOULD_MIGRATE → deplacer dans shared/types/
│
└─ Sinon → OK, rester local
```
