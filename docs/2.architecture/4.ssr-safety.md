# SSR Safety

- Role: rappeler les invariants SSR du projet et documenter les patterns à appliquer.
- Related: [./1.application-architecture.md](./1.application-architecture.md), [./13.routing-and-middleware.md](./13.routing-and-middleware.md)

## Principe

Le projet est SSR-safe par défaut. Toute dépendance au DOM, à `window` ou au contexte
client doit être isolée explicitement. Les balises SEO et le rendu critique doivent
être calculables côté serveur.

## Les quatre guards

### 1. `import.meta.server` / `import.meta.client`

Pour conditionner l'exécution d'un bloc selon l'environnement courant.

```ts
// Dans un middleware : exécution client uniquement
export default defineNuxtRouteMiddleware(() => {
  if (import.meta.server) return
  // logique client-only...
})

// Dans un composable : accès DOM protégé
if (!import.meta.client) return

// Dans un composable : branche serveur/client distincte
if (import.meta.client) {
  // chargement différé côté client seulement
}
```

Préférer `import.meta.server` / `import.meta.client` à `process.server` / `process.client`
(tree-shaking plus fiable en Nuxt 3).

### 2. Plugin suffixé `.client.ts`

Pour un plugin qui ne doit s'exécuter que côté client. Nuxt garantit qu'il ne sera
jamais chargé sur le serveur — `window` et le DOM peuvent y être utilisés librement.

```ts
// app/plugins/deferred-runtime.client.ts
export default defineNuxtPlugin((nuxtApp) => {
  // window, requestIdleCallback, addEventListener : autorisés ici
  window.addEventListener('pointerdown', markPassiveReady, { once: true, passive: true })
})
```

### 3. `onMounted()` et `onNuxtReady()`

Pour les effets de bord qui nécessitent le DOM ou une pleine hydratation.

```ts
// Accès DOM après montage
onMounted(() => {
  const el = document.getElementById('target')
})

// Après hydratation complète de l'app
onNuxtReady(() => {
  scheduleRuntimeReady()
})
```

Ne pas accéder au DOM en dehors de ces hooks — cela provoquerait une erreur serveur
ou un mismatch d'hydratation.

### 4. `<ClientOnly>`

Pour les composants qui ne peuvent pas rendre côté serveur (dépendance DOM totale,
bibliothèque client-only).

```vue
<ClientOnly>
  <HeavyClientComponent />
  <template #fallback>
    <SkeletonPlaceholder />
  </template>
</ClientOnly>
```

Le slot `#fallback` évite un saut visuel à l'hydratation en servant un placeholder
côté serveur.

## `useState` vs `ref`

`ref()` crée un état local au composant ou au composable. Sa valeur n'est pas
transférée du serveur au client — si elle diffère entre les deux, c'est un mismatch.

`useState()` crée un état partagé et sérialisé entre SSR et client, identifié par
une clé unique. Il est récupéré tel quel côté client sans recalcul.

```ts
// ❌ Risque de mismatch si la valeur est calculée différemment côté serveur
const isReady = ref(false)

// ✅ État survivant à l'hydratation, cohérent serveur/client
const isReady = useState<boolean>('deferred.runtime.ready', () => false)
const locale  = useState<LocaleCode>('locale.setting', () => FALLBACK_LOCALE)
```

Utiliser `useState` pour :
- tout état qui doit être cohérent entre SSR et hydratation
- les flags de bootstrap ou de locale
- les états partagés entre plusieurs composants via une clé stable

## Risques d'hydratation

### Valeurs dépendantes du temps ou de l'aléatoire

```ts
// ❌ Valeur calculée différemment côté serveur et client
const label = computed(() => new Date().toLocaleDateString())

// ✅ Calculer côté client uniquement
const label = ref('')
onMounted(() => { label.value = new Date().toLocaleDateString() })
```

### Accès DOM synchrone hors hook

```ts
// ❌ window n'existe pas côté serveur
const width = ref(window.innerWidth)

// ✅
const width = ref(0)
onMounted(() => { width.value = window.innerWidth })
```

### État Pinia initialisé différemment selon l'environnement

Le state des stores Pinia doit être sérialisable et produire la même valeur initiale
côté serveur et côté client. Éviter les valeurs dérivées de `Date`, `Math.random()` ou
de `window` dans `state()`.

## SEO et rendu serveur

Les données critiques pour le SEO doivent être calculables côté serveur :

- `useSeoMeta()` doit recevoir des valeurs résolues, pas des `ref` indéfinies
- `useSchemaOrg()` et les JSON-LD doivent être complets au premier rendu
- les balises Open Graph (`ogImage`, `ogTitle`) doivent avoir une valeur de fallback
  si la donnée n'est pas encore chargée

```ts
// ✅ Valeur toujours définie, même si la page n'est pas encore chargée
useSeoMeta({
  title: page.value?.metaTitle ?? siteConfig.name,
  description: page.value?.metaDescription ?? '',
})
```

## Middleware SSR

Un middleware global s'exécute côté serveur et client. Toute logique client-only doit
être gardée explicitement :

```ts
export default defineNuxtRouteMiddleware((to, from) => {
  if (import.meta.server) return          // SSR : ne pas exécuter
  if (!from.matched.length) return        // hydratation initiale : laisser passer
  // logique client-only...
})
```

## Règles de synthèse

- pas de `window`, `document` ou DOM sans guard `import.meta.client`, `onMounted` ou plugin `.client.ts`
- pas de valeurs temporelles ou aléatoires dans des `computed` rendus côté serveur
- préférer `useState` à `ref` pour tout état partagé entre SSR et hydratation
- les slots `#fallback` de `<ClientOnly>` évitent les sauts visuels à l'hydratation
- le SEO (`useSeoMeta`, JSON-LD) doit avoir des valeurs de fallback exploitables dès le rendu serveur
- toute logique fragile à l'hydratation doit être isolée et documentée localement
